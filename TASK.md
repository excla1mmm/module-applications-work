# module-applications — приём сторонних модулей MikoPBX по PR-заявке

Сводное ТЗ: голосовые от 27.10.2026, задачи Jira LIC-611/612/613/614, эпик LIC-309, разбор
[anthropics/oss-scanner](https://github.com/anthropics/oss-scanner) и нашей заявки там
([PR #745](https://github.com/anthropics/oss-scanner/pull/745)).
Составлено 27.10.2026.

---

## 1. Суть в одном абзаце

Сторонний автор хочет разместить модуль в маркетплейсе MikoPBX. Он открывает PR в публичный репозиторий
`module-applications`, добавляя один каталог `applications/<module_id>/` с манифестом заявки (исходники остаются
в его репозитории, в манифесте — URL и **полный commit SHA**). Роботы GitHub Actions проверяют формат, принятие
условий/подпись соглашения, собирают модуль из закреплённого SHA, ставят его в свежий Docker MikoPBX (x86_64 и arm64),
гоняют установку/запуск/удаление, затем AI-агент (Claude) пишет отчёт: блокеры со ссылками на требования
отдельно от рекомендаций. Дальше либо автор исправляет, либо сотрудник MIKO вручную одобряет **конкретный SHA**.
После merge отдельный доверенный workflow регистрирует модуль за подтверждённым издателем на сервере лицензий.
Принятая заявка остаётся в репозитории как реестр допущенных модулей. Публикация версий — отдельная операция в кабинете.

Цепочка: **свой репозиторий → PR-заявка → автопроверки + AI-отчёт → исправления → решение человека → merge →
регистрация модуля → загрузка версий в кабинете.** Каждый новый GUID — отдельная заявка.

## 3. Референс: как устроен anthropics/oss-scanner

### 3.1. Структура репозитория

```
README.md, CONTRIBUTING.md, CLA.md, SECURITY.md, CODE_OF_CONDUCT.md
templates/project.yaml, Dockerfile, threat_model.md     ← шаблоны для заявителя
tools/validate.py            ← офлайн-валидатор каталога projects/<name>/ (те же правила, что у сканера)
tools/check <name>           ← локально: validate → clone repo → docker build → слой сканера → shell без сети
tools/check_build.py, check_qemu.py
.github/PULL_REQUEST_TEMPLATE.md   ← чек-лист заявителя
.github/CODEOWNERS                  ← 5 ревьюеров на всё
.github/workflows/build.yaml, cla.yaml, terms.yaml, triage.yaml
.github/scripts/triage.py           ← сбор фактов для ревьюера (~940 строк)
projects/<name>/project.yaml        ← реестр принятых (185 проектов)
```

Принимают **только** PR, меняющие один `projects/<name>/`; изменения в `tools/`, `templates/` не принимаются.

### 3.2. Манифест `project.yaml`

| Поле | Обяз. | Смысл |
|---|---|---|
| `repo` | да | https URL одного репо, опц. `#branch`/`#tag` |
| `primary_contact` | да | один email, публичный |
| `auto_ccs` | нет | доп. адреса (несовместимо с `pgp`) |
| `homepage` | нет | https |
| `pgp` | нет | armored ключ для шифрования отчётов |
| `output_format` | нет | min_severity по каналам |
| `disabled` | нет | пауза без удаления |
| `dockerfile` | да* | путь в репо проекта, иначе `Dockerfile` рядом с yaml |
| `threat_model` | нет | путь в репо, иначе файл рядом |

Правила валидатора: whitelist ключей; **операторские ключи** (`budget`, `schedule`, `priority`, `workflow`…) PR
задавать не может; имя каталога `^[a-z0-9][a-z0-9._-]{0,62}$`; рядом с yaml только `Dockerfile`/`threat_model.md`,
каждый файл ровно в одном месте; лимиты размера (64/128 КБ); пути без `..`; регексы email/URL.

### 3.3. Чек-лист PR (шаблон)

Core maintainer; принимаю условия (ссылка); проект соответствует критериям; validate проходит; check собирает,
тесты идут; primary_contact — security-контакт; Dockerfile на месте; threat model (рекомендуется).
Подпись CLA — комментарием-фразой. Опционально — обоснование «почему проект достоин».

### 3.4. Workflows — главное, что копируем по паттернам безопасности

| Workflow | Что делает | Приёмы безопасности |
|---|---|---|
| `terms.yaml` | Падает, пока в описании PR не отмечен чекбокс «I accept the terms» (регекс). Перезапуск на `edited`. | `pull_request_target`, токен не выдаётся (`permissions: {}`), тело PR — только через env, не `${{ }}` в скрипт |
| `cla.yaml` | CLA Assistant: бот просит подписать, подпись = комментарий с фразой, хранится в ветке `cla-signatures`. Защита от подмены: автор PR должен быть автором коммита | allowlist ботов/мейнтейнеров |
| `build.yaml` | Собирает проект `tools/check --no-shell` | `pull_request_target`, checkout **базовой** ветки; из PR берутся только файлы `projects/<name>/` из git object store; проверка «ровно один проект, ничего вне», только regular files; Dockerfile исполняется только внутри `docker build`; **никаких секретов, кэшей, артефактов, write-прав**; `::stop-commands::` вокруг логов сборки |
| `triage.yaml` | Комментарий-таблица для ревьюера | Разделён на `gather` (read-only токен, PR как данные) и `comment` (единственное write-право, только постит текст) |

Комментарий triage (на нашем PR #745): возраст/активность репо, звёзды/форки, внешние участники, OpenSSF criticality,
ранг пакета, лицензия, автор PR — активный мейнтейнер?, контакт есть в `SECURITY.md`?, OSS-Fuzz, наличие
`.oss-scanner/` в репо, scope PR, validate, чек-лист. Подпись: «решает ревью, бот только информирует».

### 3.5. Наша заявка #745 (MikoPBX Core) — пример «прошла роботов, ждёт человека»

- Один файл `projects/mikopbx/project.yaml`; Dockerfile и threat model лежат в `mikopbx/Core/.oss-scanner/`.
- Все проверки зелёные (build, CLA, terms, triage); `REVIEW_REQUIRED` с 18.10.2026 — ждёт одного из 5 CODEOWNERS.
- В описании — контекст, верификация (validate, check, phpunit офлайн, amd64+arm64) и нюанс для сканера
  (loopback обходит auth и WAF).

### 3.6. Ключевое отличие от нас

У Anthropic проверка до merge — только формальная + сборка, а **сканирование идёт после merge** их закрытым
сервисом. У нас **AI-проверка и тесты модуля — до merge** и являются условием одобрения. Плюс регистрация на нашем
сервере лицензий после merge. Т.е. oss-scanner — референс формата подачи, контактов и паттернов безопасности
workflows, а не готовый gate (прямо оговорено в LIC-611/612).

## 4. Целевая архитектура

### 4.1. Репозитории

| Репо | Что в нём |
|---|---|
| `mikopbx/module-applications` (новый, публичный) | Документация RU/EN, шаблон манифеста, правила (версионированные), валидатор, фикстуры, workflows, `applications/<module_id>/` — реестр принятых |
| `module-template` (новый или на базе [mikopbx/ModuleTemplate](https://github.com/mikopbx/ModuleTemplate)) | Минимальная структура модуля для репо вендора + инструкция сборки ZIP из SHA и локального прогона тех же проверок, что в CI |
| Репо издателя | Исходники модуля; опционально `.mikopbx/` (аналог `.oss-scanner/`) — например, тестовый сценарий, описание модели угроз |
| Сервер лицензий (закрытый, модуль Releases) | API регистрации по заявке (LIC-613, не моя задача, но контракт согласуется со мной) |

### 4.2. Предлагаемая структура `module-applications`

```
README.md / README.ru.md          как подать, что будет после merge, как обновить/отозвать
CONTRIBUTING(.ru).md
TERMS.md (+ ссылка на оферту/договор)   условия размещения — аналог OSS Scanner terms
CLA.md или PUBLISHER_AGREEMENT.md       соглашение, подписываемое комментарием (аналог CLA)
rules/                             версия стандарта: обязательный контракт MikoPBX vs рекомендации, у каждого id
schema/application.schema.json     версия схемы манифеста
templates/application.yaml
tools/validate.py                  детерминированный валидатор (локально = CI)
tools/check                        локальный прогон: сборка ZIP из SHA → установка в Docker MikoPBX
tests/fixtures/{good,bad}/         положительные и испорченные заявки + контрольный модуль
.github/PULL_REQUEST_TEMPLATE.md
.github/CODEOWNERS                 ревьюеры MIKO
.github/workflows/
   terms.yaml       чекбокс условий
   cla.yaml         подпись соглашения
   validate.yaml    формат + triage-комментарий (gather/comment)
   test.yaml        матрица Docker MikoPBX × архитектуры — недоверенный код, без секретов
   ai-review.yaml   доверенный агент Claude, читает исходники/логи как данные
   register.yaml    после merge → API сервера лицензий (LIC-613)
applications/<module_id>/application.yaml   реестр (одна заявка = один каталог = один GUID)
```

### 4.3. Черновик манифеста `application.yaml` (согласовать с LIC-319)

```yaml
schema_version: 1
module_id: ModuleExample            # = moduleUniqueID в module.json на этом SHA (GUID ReleasesTypes)
publisher_id: 42                    # НЕ доказательство личности — сверяется с подтверждённым издателем
name: Example module
description: Что делает модуль (кратко)
repo: https://github.com/vendor/ModuleExample
commit: 0123456789abcdef0123456789abcdef01234567   # полный 40-hex SHA; ветка/тег/короткий SHA не принимаются
license: GPL-3.0-or-later           # SPDX
support_email: support@vendor.example   # публичный; должен совпадать с карточкой издателя
maintainers: [vendor-login]         # кто поддерживает (GitHub)
homepage: https://vendor.example    # опц.
compatibility:
  min_pbx_version: "2024.1.0"       # согласован с module.json
  max_pbx_version: null
  architectures: [x86_64, arm64]    # определяет тестовую матрицу
```

Операторские поля (уровень доверия `community/verified`, платность, образы, правила, бюджет) — **только у MIKO**,
PR их задать не может (аналог `OPERATOR_KEYS`). `contact_email` (приватный) в публичный репо не кладём.
Обязательный `repo` здесь ≠ опциональный `source_url` каталога (LIC-309/317/338) — развести явно.

`module.json` из ModuleTemplate для сверки: `developer`, `moduleUniqueID`, `support_email`, `version`, `min_pbx_version`.

### 4.4. Три доверительных контура (жёсткое требование LIC-612/614)

| Контур | Что исполняет | Секреты | Где |
|---|---|---|---|
| **Тесты** | Чужой код: сборка ZIP, Docker MikoPBX (возможно privileged), установка/удаление | **Никаких**: нет ключа Anthropic, ключа лицензирования, привилегированного GitHub-токена, docker socket хоста не пробрасывать, нет доступа во внутреннюю сеть | одноразовый GitHub-hosted runner; граница изоляции — вся ВМ |
| **AI-отчёт** | Доверенный код анализатора MIKO; исходники и логи — только как данные | только ключ Anthropic | отдельная ВМ; не грузит hooks/plugins/MCP/CLAUDE.md из модуля; политика и инструменты — MIKO |
| **Регистрация** | Только доверенный workflow на защищённой ветке после merge | только ключ сервера лицензий (ограниченные права, LIC-596) | отдельная ВМ; не запускает MikoPBX и файлы PR |

Передача результатов между контурами: проверять происхождение запуска, актуальность ревизии/SHA, завершённость
всех обязательных этапов. Артефакт/кэш недоверенного job сам по себе не доказательство. Пустой отчёт, таймаут,
ошибка, исчерпанный бюджет = **не пройдено**. Push после одобрения / смена SHA или манифеста сбрасывают проверки и одобрение.

`pull_request_target` — только для чтения PR как данных (как в oss-scanner); исполнять чужой код с секретами нельзя.

## 5. Задачи Jira

Порядок: **LIC-611 → LIC-612 → (LIC-613, не моя) → LIC-614.** LIC-611 блокирует 612 и 613; 614 блокируется всеми тремя.
Эпик LIC-309, спринт 37 (future) «Модули 3 — чтение и контракт».

### LIC-611 — module-template и PR-манифест в module-applications

Цель: воспроизводимая подача модуля с исходниками в репо издателя.

- [ ] Схема + пример манифеста: module_id, publisher_id, описание, совместимость, лицензия, публичный контакт поддержки, URL репо, полный SHA.
- [ ] module-template: минимальная структура + инструкция сборки/проверки; обязательный контракт MikoPBX отделён от стилевых рекомендаций; версии стандарта и схемы зафиксированы.
- [ ] Детерминированный валидатор: обязательность/форматы, уникальность module_id, совпадение id и совместимости с `module.json` на SHA, существование коммита, совпадение публичного контакта с карточкой издателя.
- [ ] Фикстуры (+/−): пропущенные поля, невалидный SHA, отсутствующий коммит, конфликт GUID, несовместимый `module.json`.
- [ ] Описано: новая заявка на каждый модуль, обновление заявки, передача результата следующему этапу без исходников.
- [ ] Обязательный `repo` отделён от опционального `source_url`; решение по непубличным исходникам и по уже допущенным модулям зафиксировано до пилота.
- [ ] (доп. 21.10) Сборка ZIP из SHA и запуск проверок на существующем образе MikoPBX документированы; локальные команды = CI.
- [ ] Совместимость в заявке задаёт версии MikoPBX и архитектуры для матрицы; образы/скрипты/правила — из доверенной конфигурации MIKO.
- [ ] Контрольный небольшой модуль + ожидаемые результаты установки/запуска/удаления; испорченные фикстуры доказывают, что gate ловит нарушения.

Проверка: валидатор на фикстурах + пробная заявка по закреплённому SHA.
Вне скоупа: регистрация через API, токены, публикация релизов, платформа модерации.

### LIC-612 — изолированные проверки, AI-отчёт, одобрение точного SHA

Схема пилота: GitHub Actions (публичный репо, стандартные runners бесплатны) + готовые Docker-образы MikoPBX + Claude (Agent SDK).

- [ ] Из манифеста извлекается ровно закреплённый SHA; сначала детерминированные проверки контракта и тесты, затем AI.
- [ ] Свежий контейнер MikoPBX на GitHub-hosted runner; матрица версий × архитектур (x86_64/arm64 на native runners); в отчёте версия, арх., digest образа.
- [ ] Из SHA собирается ZIP, сохраняется checksum; штатная установка; проверить: появление/включение, сервисы и API, ошибки в логах, функциональные тесты, отключение, удаление, жив ли MikoPBX после удаления; обновление с предыдущей версии (или явное «первая версия»).
- [ ] Изоляция по §4.4; лимиты ресурсов, сети, очистка определены и проверены.
- [ ] AI — доверенный анализатор; файлы и отчёты модуля — данные, инструкции из них не меняют политику (prompt injection).
- [ ] Результат: module_id, publisher_id, repo, SHA, версия правил, выполненные проверки и итоги; блокеры (безопасность/обязательный стандарт) со ссылкой на требование отдельно от рекомендаций.
- [ ] AI не заменяет тесты и решение человека; таймаут/ошибка/неполнота ≠ успех.
- [ ] MIKO вручную одобряет SHA + ревизию манифеста + подтверждённого издателя; любые изменения сбрасывают одобрение; merge только с актуальными результатами.
- [ ] Негативные прогоны: чужой тест не читает секреты/внутреннюю сеть; поддельный артефакт не принимается; push после одобрения делает допуск неактуальным.

Бюджет:
- [ ] До первого платного запуска проверить в Anthropic Console кредит $100: баланс, срок, ограничения. Ключи не класть в Jira/исходники/отчёты.
- [ ] Первые $10 — калибровка на нескольких маленьких модулях, включая намеренно сломанный: пойманные/пропущенные нарушения, время, токены, число шагов, фактическая стоимость по Console.
- [ ] После калибровки — лимиты денег/шагов/времени на прогон, повторы, частота; не звать AI после провала дешёвых проверок; кэш результата только при совпадении SHA, checksum, манифеста, правил, окружения и конфигурации агента.
- [ ] Срок хранения тяжёлых артефактов; долговечная запись SHA/checksum/решений.
- Ориентир: $0.5–2 за прогон малого модуля (не замер): $100 ≈ 50–200 прогонов.

Начать с: точные ссылки на образы MikoPBX → одна контрольная заявка → воспроизводимый сценарий установки/проверки/удаления → подключить AI и замер расхода.

### LIC-613 — API регистрации (сервер лицензий, **не назначена на меня**, но я — потребитель)

Что мне важно знать для контракта: издатель — строка `Publishers` (по стабильному `github_id`), а не `publisher_id`
из YAML; регистрация принимает доверенное свидетельство (module_id, подтверждённый издатель, repo, SHA, ревизия
манифеста, checksum ZIP, версии правил, ссылки на результаты матрицы, AI-отчёт, решение человека); идемпотентна
(повтор/гонка → одна карточка); чужой module_id не перехватывается; регистрация **не публикует** версии.
Endpoint и аутентификацию выбирают в LIC-613.
Связано: LIC-553 (защита идентичности), LIC-596 (ограниченные ключи), LIC-598 (поля автора), LIC-318/338 (кабинет, GitHub OAuth), LIC-615 (гейт релизов).

### LIC-614 — доверенная регистрация после merge

- [ ] Только фактически merged PR из защищённой ветки; закрытый без merge, ручной запуск с произвольным YAML, непрошедшая заявка — отказ.
- [ ] До вызова API сверяется вся связка (заявка, ревизия, module_id, издатель, repo, SHA, правила, проверки, одобрение); HEAD/тег не подменяют SHA.
- [ ] Не исполняет код из PR/репо издателя рядом с секретами; не `pull_request_target` с чужим кодом; fork PR без секретов.
- [ ] Ограниченная служебная идентичность; полный ключ тенанта никуда не передаётся.
- [ ] Идемпотентность: повтор, таймаут после записи, параллельный запуск → одна карточка; конфликт → стоп, не перезапись.
- [ ] Результат/ошибка видны в GitHub: ссылки на PR, run, SHA, серверный id модуля; без токенов.
- [ ] Не загружает ZIP и не публикует версии.
- [ ] (доп.) Защищённая ветка требует обязательных проверок и одобрения; workflows/правила защищены от подмены заявкой; учтены права обхода защиты.
- [ ] Ключ Anthropic — только у AI-этапа, ключ лицензирования — только у регистрации.

Проверка: на тестовом API — merged одобренная заявка, PR без merge, замена SHA/манифеста, поддельный отчёт,
потеря HTTP-ответа, два параллельных запуска. Приложить URL тестового run.

## 6. Что взять у oss-scanner один-в-один (адаптировав)

### 7a. Найденные ответы (облачная сессия-исполнитель, 27.10, ветка claude/stoic-goldberg-n01ons)

1. **Образы — отвечено.** Docker Hub `mikopbx/mikopbx:2026.6.34` (= `latest`), multi-arch index
   `sha256:ff5cc0238a4e170bfbf8c0be9a59b58c8affb6fb24b36d1506f5fc0cb41f7691`: amd64 `sha256:50ed8982…f1d5d`,
   arm64 `sha256:3af27a8e…b6a6c`; есть `dev` = 2026.6.43-dev. `--privileged` не нужен (проверено на x86_64 в Docker),
   тома не нужны, старт REST API ~18 с. С `--network none` не загружается (Asterisk без интерфейса) → используется
   `docker network create --internal` + iptables на мост. На GitHub runner и arm64 — ещё не проверено (песочница, Mac).
   Подробно: `module-applications/docs/mikopbx-docker.md`.
4. **Список требований — частично.** Собран из Core develop @e7e2109, ModuleTemplate и спецификации
   `docs/third-party-modules-spec`: `module-applications/rules/rules.yaml` (rules 0.1.0, у каждого id; mandatory vs
   recommended; спорные — `status: draft` для LIC-319). Канонический список по-прежнему за LIC-319.
10. **module-template — решено (предложение исполнителя).** Каталог `module-template/` внутри module-applications:
    минимальный модуль, который проходит все проверки, + инструкции RU/EN по сборке ZIP из SHA (`tools/package`) и
    локальному прогону (`tools/validate.py`, `tools/check`). Шаблон версионируется вместе с правилами и схемой и
    проверяется тестом; `mikopbx/ModuleTemplate` не трогаем (полный пример с UI остаётся там).

Попутно выяснено (не было в вопросах):
- module_id: Core принимает `^[A-Za-z0-9_-]{1,128}$`, REST v3 адресует только `^[A-Za-z][A-Za-z0-9]*$`, спецификация
  маркетплейса — `^Module[A-Za-z0-9]{1,60}$`; в схеме заявки взято последнее (пересечение всех трёх).
- `min_pbx_version` в module.json Core сравнивает `version_compare` только при установке; ниже 2020.2.468 (или пусто,
  или `%ModuleVersion%`) — модуль ставится, но отключается при следующем обновлении АТС. Поэтому правило MJ-003.
- `version` Core не проверяет; `%ModuleVersion%` из ModuleTemplate ставится как есть. Сборка заменяет его на
  `0.0.0-<12 hex коммита>`.
- MikoPBX 2026.6.34 отличается от Core develop: `uninstall` без `keepSettings` падает, `GET /modules` (getList) не
  реализован, `getInstallationStatus` не работает с новым конвейером установки.
- `repo` (обязательный) и `source_url` каталога (опциональный) разведены в CONTRIBUTING; решение по непубличным
  исходникам и старым модулям — за владельцем (вопрос 6 остаётся).

Открытыми остаются 2, 3, 5, 6, 7, 8, 9 и часть 4.
