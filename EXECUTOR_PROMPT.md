## Этап 1 — LIC-611: формат заявки и формальная проверка
Структура репозитория — по TASK.md §4.2. Сделать:
- `schema/application.schema.json` (с версией) и `templates/application.yaml` — по черновику TASK.md §4.3.
  Поля, которыми управляет только оператор (уровень доверия, платность, образы, бюджет), PR задать не может,
  как `OPERATOR_KEYS` у oss-scanner. Полный SHA — 40 hex; ветка, тег или короткий SHA отвергаются.
- `rules/` — версионированный список требований, у каждого свой id; обязательный контракт MikoPBX отделён
  от рекомендаций. Требования бери из Core и ModuleTemplate. Сомнительные помечай как черновик для LIC-319.
- `tools/validate.py` — детерминированный, работает офлайн для формата и онлайн для проверки репозитория по SHA:
  - обязательные поля и форматы, whitelist ключей;
  - имя каталога совпадает с module_id;
  - коммит существует;
  - `module.json` на этом SHA: moduleUniqueID == module_id, min_pbx_version согласован с compatibility;
  - support_email совпадает;
  - уникальность module_id в `applications/`;
  - заглушка сверки с сервером.
  Коды выхода и формат сообщений — как в oss-scanner.
- `tests/fixtures/` — правильные заявки и испорченные: пропущенные поля, невалидный SHA, несуществующий коммит,
  конфликт GUID, несовместимый module.json, операторский ключ, файл вне каталога. Плюс тесты (pytest) на всё это.
- Контрольный модуль — небольшой, в отдельном публичном или локальном репозитории, на основе ModuleTemplate.
  К нему — заявка с ожидаемыми результатами установки, запуска и удаления.
- Документация на русском и английском: README, CONTRIBUTING (как подать новую заявку, как обновить, как отозвать).
  Сюда же TERMS и соглашение издателя — как черновики с пометкой «текст утверждает MIKO», юридический текст
  не выдумывай. Плюс `.github/PULL_REQUEST_TEMPLATE.md` с чек-листом.
- Workflows, по паттернам безопасности oss-scanner:
  - `terms.yaml` — чекбокс в описании PR, без токена, тело PR только через env;
  - `cla.yaml` — подпись соглашения комментарием;
  - `validate.yaml` — base checkout, из PR берутся только файлы одного `applications/<id>/`; triage-комментарий
    разделён на два job: gather с read-only правами и comment с единственным правом на запись.
- Шаблон модуля для вендора — инструкция сборки ZIP из SHA и локального прогона тех же проверок.
  Вариант: каталог `module-template/` или доработка ModuleTemplate — выбери и обоснуй в Jira.

## Этап 2 — LIC-612: изолированные тесты (без AI)
- `tools/check <module_id>` — локально и в CI один и тот же код:
  validate → клонировать repo на точном SHA → собрать ZIP, записать sha256 → поднять свежий контейнер MikoPBX
  (образ и digest берутся из доверенного конфига MIKO в репозитории, не из заявки) → установить штатным способом →
  проверить, что модуль появился и включён, его сервисы и API (если есть), ошибки в логах →
  отключить → удалить → проверить, что MikoPBX жив → JSON-результат.
  В результате: module_id, SHA, sha256 ZIP, версия правил, версия MikoPBX, архитектура, digest образа,
  выполненные шаги и итог.
  Сценарий обновления: если первая версия, явно пишется «не применимо».
- `.github/workflows/test.yaml` — матрица `ubuntu-latest` (x86_64) и `ubuntu-24.04-arm` (arm64):
  - `permissions: {}` или только `contents: read`;
  - никаких секретов, кэшей и токенов с правом записи;
  - чужой код исполняется только внутри контейнера и сборки;
  - логи сборки и тестов обёрнуты в `::stop-commands::`;
  - результат — артефакт с коротким сроком хранения.
  В комментариях к workflow опиши модель угроз, как это сделано в oss-scanner.
- Негативные проверки, с подтверждением на реальных прогонах:
  - модуль, который пытается прочитать env или секреты и сходить во внутреннюю сеть или metadata, ничего не получает;
  - сломанный модуль — тест красный;
  - PR, затрагивающий файлы вне своего каталога или workflows, отвергается до исполнения кода.
- Пробная заявка контрольного модуля проходит; испорченная — падает с понятной причиной.
