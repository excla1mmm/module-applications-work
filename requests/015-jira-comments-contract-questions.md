### Комментарий 1 — LIC-614

```
Вопросы к контракту LIC-613/LIC-615 от GitHub-части

Контекст: после merge заявки в mikopbx/module-applications доверенный workflow (только код из ветки по умолчанию, отдельный job с ограниченными правами) должен зарегистрировать GUID за издателем через API LIC-613. Ниже — что GitHub-части нужно знать, с нашим предложением. Конкретные адреса и форматы — за сервером.

1. Аутентификация workflow на сервере.
   Варианты: (а) OIDC-токен GitHub Actions (audience = сервер; сервер проверяет подпись GitHub и claims: repository = mikopbx/module-applications, ref = ветка по умолчанию, workflow, environment); (б) ограниченный ключ в отдельном Environment с обязательным ревьюером.
   Предложение: (а) — без долгоживущего секрета, сервер видит, какой workflow и с какой ветки вызвал. Вопрос: поддержит ли сервер OIDC? Если нет — (б), ключ только на регистрацию, с ротацией.
2. Что передаём (доверенное свидетельство). Предложение: номер PR, merge SHA, SHA ревизии заявки (blob application.yaml), module_id, repo, source commit SHA, sha256 ZIP (и sha256 тестовой копии для платного модуля), версии правил и схемы, образ MikoPBX и digest, архитектуры, run id тестов и AI-ревью, кто одобрил (GitHub-логины ревьюеров и время). Вопрос: какие поля сервер считает обязательными, а какие проверит сам?
3. Как сервер проверяет происхождение. Варианты: (а) доверяет OIDC-claims и сам перепроверяет по GitHub API (PR смержен, merge SHA в ветке по умолчанию, файл заявки в merge SHA совпадает, run'ы успешны на этом head); (б) доверяет только свидетельству. Предложение: (а) — свидетельство как подсказка, факты сервер берёт из GitHub сам.
4. Идемпотентность. Предложение: ключ module_id + merge SHA; повтор с тем же ключом и теми же данными — тот же ответ; тот же ключ с другими данными — ошибка. Вопрос: согласен ли сервер, или ключ выдаёт сервер?
5. Ошибки, которые workflow должен различать: GUID занят другим издателем; издатель не подтверждён / заблокирован; связка устарела (заявка или пакет поменялись после одобрения); недоступность сервера (повтор) vs окончательный отказ (повтор не нужен, нужен человек). Вопрос: коды/категории ответов и что из них повторять.
6. Подтверждение издателя. Кабинет связывает издателя с GitHub по github_id. Предложение: сервер находит карточку по стабильному github_id автора PR (и/или maintainers), а publisher_id в заявке — только подсказка для триажа или убирается из схемы. Вопрос: нужен ли publisher_id в заявке; какой github_id считать издателем (автор PR, автор коммита заявки, кто подписал соглашение)?
7. До готовности API. Сейчас сверка — заглушка not_checked, это не успех; merge фиксирует допуск, регистрации после merge нет, модуль регистрируется вручную после проверки издателя MIKO. Вопрос: подтверждает ли сервер, что при появлении API регистрация заявки с not_checked невозможна (сервер проверяет издателя сам), и нужна ли повторная регистрация для заявок, смерженных до API?
8. Аудит. Артефакты GitHub хранятся 7 дней. Вопрос: что сервер хранит у себя долговременно (свидетельство целиком? отчёты?), чтобы не зависеть от сроков GitHub.
```

### Комментарий 2 — LIC-662

```
Вопросы к контракту LIC-613/LIC-615 от GitHub-части

Контекст: выпуск версии допущенного GUID по точному SHA. Сервер (LIC-615) запускает доверенный workflow в mikopbx/module-applications; workflow собирает воспроизводимый ZIP из SHA, прогоняет те же проверки (tools/check x86_64/arm64, AI-ревью), отдельный job передаёт на сервер те же проверенные байты и результат. Публикацию разрешает только сервер. Ниже — что GitHub-части нужно знать, с вариантами.

1. Как сервер запускает workflow. Варианты: (а) workflow_dispatch от GitHub App сервера (права только actions:write на этот репозиторий); (б) repository_dispatch. Предложение: (а) — входы типизированы и видны в UI, App с минимальными правами. Входы: job id, GUID (module_id), repo, SHA (40 hex), версия, канал/намерение (draft/stable), архитектуры. Вопрос: какой набор входов и кто владеет App.
2. Как workflow убеждается, что задание настоящее. Предложение: первым шагом спрашивает сервер по job id и сверяет все входы с ответом (сервер — источник истины, входы dispatch — только указатель); расхождение — отказ без сборки. Вопрос: подходит ли такая сверка и чем workflow аутентифицируется (см. LIC-614: OIDC или ключ в Environment).
3. Передача пакета. Предложение: отдельный job без доступа к коду модуля загружает на сервер те же байты, что тестировались (sha256 из результата тестов), служебной идентичностью; сервер сам считает checksum и сравнивает. Вопрос: один ZIP на все архитектуры или отдельные пакеты по архитектурам; для платного модуля — передаём только пакет издателя (тестовая копия с lic_* = 0 — только для тестов)?
4. Передача результата. Предложение: result.json тестов (по архитектуре) и AI-отчёт по схеме ai-report (schema/ai-report.schema.json) как есть, с версиями схем. Вопрос: нужен ли серверу свой формат или он принимает наши схемы с версией?
5. Состояния и повтор. Предложение: идемпотентный ключ — job id + sha256 пакета; повтор с тем же ключом — тот же результат; другие байты под тем же job id — ошибка (конфликт). Вопрос: какие состояния задания видит GitHub-часть (принято / собирается / проверки / ждёт решения / разрешено / отклонено) и кто их меняет.
6. Ручное решение. Если нужно решение человека — служебный PR с точной связкой версия + пакет (sha256); достаточно одного Approve проверяющего MIKO (автор PR не одобряет свой). Варианты, как сервер узнаёт об Approve: (а) webhook GitHub App сервера (pull_request_review, merge); (б) workflow после merge сообщает серверу по job id; (в) сервер опрашивает по job id. Предложение: (б) — тот же путь, что регистрация в LIC-614. Вопрос: кто создаёт служебный PR — workflow (по ответу сервера) или сервер?
7. Критерии «рискованного обновления» (когда нужно ручное решение): смена мажорной версии, новые сетевые соединения, новые права, блокеры/рекомендации AI, смена образа? Вопрос: кто их формулирует и где они живут. Предложение: в rules.yaml как правила с id (видно в отчёте, версионируется), сервер получает итог «нужно решение: да/нет, причины».
8. Хранение. Артефакты GitHub — 7 дней. Вопрос: что сервер хранит долговременно (пакет, результаты, отчёт, кто одобрил), чтобы аудит не зависел от GitHub.
9. Частные данные. contact_email и другие частные данные издателя в GitHub не передаются; workflow получает только то, что нужно для сборки и проверок. Вопрос: подтверждаем список входов из п.1 как исчерпывающий.
```
