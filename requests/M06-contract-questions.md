# M06 (от Mac / пользователя → облаку): вопросы к серверным контрактам для LIC-614 и LIC-662

Параллельно с M05 (приоритет у M05). Код не пишем — готовим вопросы и предложения со стороны GitHub, чтобы владелец
(исполнитель серверных задач LIC-613 и LIC-615 — Николай) зафиксировал контракты. **Endpoint'ы не выдумывать**:
формулировать как «что GitHub-части нужно знать / что предлагаем», с вариантами.

## Новые задачи (кратко, без внутренних деталей сервера)
- **LIC-662 (Егор): GitHub-часть выпуска версии по SHA.** Издатель запускает выпуск из кабинета → сервер запускает
  доверенный workflow в mikopbx/module-applications → сборка воспроизводимого ZIP из точного SHA → те же проверки
  (tools/check, матрица, AI) → отдельный job передаёт **те же проверенные байты** и результат на сервер лицензий.
  Обычное обновление допущенного GUID — без новой заявки; если нужно ручное решение — служебный PR с точной связкой
  версия+пакет, достаточно одного Approve проверяющего MIKO (Николай, Егор, Иван Мальцев, Алексей Портнов; автор PR
  не одобряет свой). Публикацию разрешает только сервер. Частный contact_email в GitHub не передаётся.
- **LIC-615 (Николай): серверная часть** — задание, контракт запуска GitHub, приём пакета/результата, состояния,
  разрешение публикации. Требует опубликовать контракт до реализации GitHub-части.
- **LIC-613 (Николай): API регистрации GUID по одобренной заявке** — потребитель LIC-614 (наш workflow после merge).
- **LIC-663 (Егор): полный пилот** на модуле ModuleLocalSpeechToText — после всего остального.

## Что подготовить
Два текста (markdown) для комментариев в Jira, каждый — список вопросов с нашим предложением/вариантами:

1. **Для LIC-614 → LIC-613 (регистрация после merge):**
   аутентификация служебной идентичности workflow (OIDC GitHub → сервер? ограниченный ключ в Environment?);
   формат доверенного свидетельства (PR, merge SHA, ревизия заявки, module_id, source SHA, sha256 ZIP(ов), версии
   правил/схемы, образ/digest/архитектуры, run id тестов и AI, решение человека); как сервер проверяет происхождение
   (GitHub API по run id? подпись OIDC?); идемпотентный ключ (предложение: module_id + merge SHA); коды ошибок
   (конфликт владельца/GUID, устаревшая связка, блокировка издателя, not_checked); как подтверждается издатель —
   нужен ли `publisher_id` в заявке, если сервер находит карточку по github_id автора PR (вопрос из 012); как
   работать до готовности API (что разрешено с заявкой при not_checked — см. вопрос 1 LIC-661).
2. **Для LIC-662 → LIC-615 (выпуск версии):**
   как сервер запускает workflow (repository_dispatch / workflow_dispatch от GitHub App сервера?) и какие входы
   (job id, GUID, repo, SHA, версия, канал, намерение draft/stable, архитектуры); как workflow подтверждает, что
   задание настоящее (сверка с сервером по job id?); передача пакета (загрузка байтов на сервер служебной
   идентичностью; сервер сам считает checksum) и результата (схема `ai-report` + result.json тестов); состояния и
   повтор (идемпотентный ключ job id + вариант пакета; конфликт байтов — ошибка); раздельные пакеты по архитектурам
   или один; как сервер создаёт служебный PR для ручного решения и как узнаёт об Approve (webhook / опрос по job id);
   критерии «рискованного обновления» — кто их формулирует и где они живут (rules.yaml?); срок хранения артефактов
   GitHub (7 дней) vs долговечный аудит на сервере.
