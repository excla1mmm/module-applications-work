## Критерии приёмки LIC-661 (кратко)
1. Перенос итоговой реализации через PR; в задаче — исходный и итоговый SHA, ссылка на PR. **Без истории песочницы**
   (чистый импорт). Пустой репозиторий: первый коммит (например, README/.gitignore) — прямым push до включения
   ruleset, всё остальное — PR. Ветку по умолчанию: предложи `main` (как в документации) и переименуй до включения
   защиты — или оставь `master` и поправь документацию; выбор зафиксируй.
2. README / CONTRIBUTING RU/EN, шаблон PR, пример заявки, module-template — путь издателя: свой репозиторий → заявка →
   локальная проверка → исправление замечаний CI. Все ссылки `excla1mmm/...` → `mikopbx/...`.
3. Ограничения пилота в документации: только публичный GitHub; старые модули не затрагиваются; `repo` ≠ `source_url`;
   TERMS и соглашение издателя — **неутверждённые черновики**; платные и бесплатные модули принимаются (M04).
4. Workflows, Environment `ai-review` (secret `ANTHROPIC_API_KEY` — значение кладёт пользователь сам, см. ниже),
   permissions, variables; CODEOWNERS с ревьюерами MIKO (список — от пользователя). Для настроек уровня организации
   (GitHub App для image-update, установка Claude App) — конкретный список действий для владельца.
5. Защита ветки (ruleset, без bypass): PR обязателен, **1+ одобрение**, dismiss stale on push, **require last push
   approval**, **code owners review**, strict required checks (result, gather, terms-accepted, agreement, AI review),
   запрет deletion/force push. image-update — вариант B (GitHub App) или ручное временное отключение с аудитом.
   Проверить отрицательными сценариями **в целевом репозитории**: красный PR, без одобрения, сброс одобрения после
   push (нужен второй человек — ревьюер из CODEOWNERS; запроси у пользователя, когда будет готово).
6. Пробная заявка по полному SHA проходит (x86_64 и arm64), намеренно испорченная — отклонена; ссылки на PR и Actions.
   pytest и tools/validate.py / tools/check — **только в CI целевого репозитория** (локально у пользователя ничего не гоняем).
7. Ответы на вопросы владельца (в Jira, запросом jira-write):
   1. Пока `publisher_registry` = `not_checked` (API LIC-613 нет): что можно — одобрять, мержить, регистрировать? На
      каком шаге гарантированно нельзя зарегистрировать модуль за непроверенным издателем? Зафиксировать промежуточное
      поведение в инструкции; not_checked ≠ успех.
   2. Какие настройки защиты проверены в песочнице, какие применены в целевом, что делает владелец — с подтверждением
      отрицательными проверками на целевом.
   3. Список draft-правил для LIC-319: «ID → спорный момент → предлагаемое решение»; могут ли они сейчас блокировать
      заявку (валидатор / AI).
