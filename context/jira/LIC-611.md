## Описание (Jira wiki)

h2. Цель и контекст
Дать издателю воспроизводимый способ подать новый модуль, сохранив исходники в его репозитории. Развитие MVP по плану пользователя от 21.10.2026. Существующие задачи и их исторические критерии не переписываются. Новая цепочка: заявка → проверки → ручное одобрение конкретного SHA → merge → регистрация модуля; публикация версии — отдельная операция. Без отдельной платформы модерации.
В LIC-309 уже есть издатели и допуск по GUID, но нет отдельного каталога заявок и контракта подачи по полному SHA.

h2. Границы
Подготовить module-template для репозитория вендора и отдельный каталог module-applications с PR-манифестами и инструкцией подачи. Не переносить исходники в каталог заявок. Идентификатор module_id согласовать с существующим GUID ReleasesTypes, не создавать вторую независимую идентичность.

h2. Критерии приёмки
* [ ] Зафиксированы схема и пример манифеста: module_id, publisher_id, описание, совместимость с MikoPBX, лицензия, публичный контакт поддержки, URL репозитория исходников и полный commit SHA; ветка, тег и сокращённый SHA не заменяют фиксацию коммита.
* [ ] module-template содержит минимальную структуру модуля и инструкцию сборки/проверки; обязательный контракт MikoPBX отделён от рекомендаций по стилю. Версии стандарта и схемы фиксируются.
* [ ] Детерминированный валидатор проверяет обязательность/форматы, уникальность module_id, соответствие идентификатора и совместимости module.json, доступность заданного коммита и согласованность публичного контакта с карточкой издателя. publisher_id не считается доказательством личности.
* [ ] Положительные и отрицательные фикстуры покрывают пропущенные поля, невалидный SHA, отсутствующий коммит, конфликт GUID и несовместимый module.json.
* [ ] Описаны новая заявка для каждого нового модуля, обновление существующей заявки и передача результата следующему этапу проверки без исходников в module-applications.
* [ ] Обязательный URL в новом процессе заявок явно отделён от прежнего опционального source_url каталога (LIC-309/317/338). Решение о доступе к непубличным исходникам и применимости нового процесса к ранее допущенным модулям зафиксировано до пилота, без молчаливого изменения старого API.

h2. Зависимости и открытые решения
Следующий этап — задача «Изолированные проверки, AI-отчёт и одобрение точного SHA»; подтверждение издателя и регистрация — отдельная задача API. Канонический состав обязательных требований и отображение полей в ReleasesTypes согласовать с LIC-319.
Референс только формата подачи repo/контактов: https://github.com/anthropics/oss-scanner — его README описывает сканирование после merge; это не подтверждение AI-проверки PR до merge.

h2. Проверка и вне скоупа
Прогон валидатора на фикстурах и пробная заявка по закреплённому SHA. Вне скоупа: регистрация через API, выпуск токенов, публикация релизов, отдельная система модерации. Эта Jira-задача описывает будущую реализацию; в рамках текущего запроса репозитории и код не создаются.

h2. Дополнение 21.10.2026 — готовая среда MikoPBX и воспроизводимая заявка
Владелец подтвердил наличие готовых Docker-образов MikoPBX для нужных архитектур. Основа пилота — существующие образы и публичный open-source репозиторий module-applications с GitHub Actions; создавать новое окружение MikoPBX с нуля не требуется. Конкретные registry/image/digest пока не переданы и должны быть установлены при старте разработки, без угадывания URL.
* [ ] В шаблоне документированы сборка ZIP из закреплённого SHA и запуск проверок на существующем образе MikoPBX; команды локального воспроизведения используют тот же проверяющий набор, что CI.
* [ ] Совместимость в заявке позволяет определить версии MikoPBX и поддерживаемые архитектуры для тестовой матрицы. Образы/проверяющие скрипты и правила берутся из доверенной конфигурации MIKO, а не произвольно переопределяются PR издателя.
* [ ] В примере заявки есть небольшой контрольный модуль и ожидаемые результаты установки/запуска/удаления для пилота LIC-612. Положительные и намеренно испорченные фикстуры проверяют, что gate действительно обнаруживает нарушение.
Согласованный путь издателя: свой репозиторий → PR-заявка → автоматические проверки и AI-отчёт → исправления → решение человека → merge и регистрация → загрузка версий в кабинете. Каждый новый GUID проходит отдельную заявку; модуль остаётся в репозитории издателя.
