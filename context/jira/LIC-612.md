## Описание (Jira wiki)

h2. Цель и контекст
Проверить модуль до допуска по PR-заявке так, чтобы недоверенный код не получал секреты и не мог подменить результат проверки. Развитие MVP по плану пользователя от 21.10.2026. Существующие задачи и их исторические критерии не переписываются. Новая цепочка: заявка → проверки → ручное одобрение конкретного SHA → merge → регистрация модуля; публикация версии — отдельная операция. Без отдельной платформы модерации.
ZipInspector из LIC-313 остаётся структурной проверкой ZIP без исполнения; он не заменяет проверку исходников и обязательного стандарта.

h2. Границы
Переиспользовать существующие средства CI и небольшой доверенный анализатор/прослойку вызова AI. Отдельную платформу модерации не строить. Не предполагать наличие какого-либо готового скилла проверки модулей: уточнение пользователя касалось Jira-скилла.

h2. Критерии приёмки
* [ ] По валидному манифесту извлекается ровно закреплённый commit SHA. Сначала выполняются детерминированные проверки обязательного стандарта/контракта и тесты модуля, затем формируется AI-отчёт.
* [ ] Сборка и исполнение любого кода из репозитория/PR идут в изолированной одноразовой среде: без секретов лицензирования, AI API key, привилегированного GitHub-токена, host socket/служебных mounts и доступа к внутренним сервисам. Ограничения ресурсов, сети и очистка определены и проверены.
* [ ] AI вызывает доверенный код анализатора, а не workflow с исполнением чужого кода и выданными ему секретами. Недоверенные файлы и отчёты рассматриваются как данные; инструкции из них не меняют политику допуска или команды доверенной части.
* [ ] Результат содержит module_id, publisher_id, URL исходников, полный SHA, версию правил, выполненные проверки и их результаты; блокирующие нарушения обязательного стандарта/безопасности со ссылками на требования отделены от рекомендаций.
* [ ] AI-отчёт не заменяет обязательные тесты и ручное решение. Таймаут/ошибка/неполный результат не считаются успешной проверкой.
* [ ] MIKO вручную одобряет конкретный SHA вместе с ревизией манифеста и подтверждённым издателем; изменение SHA, манифеста, личности или применимых правил сбрасывает прежние проверки и одобрение. Merge допускается только с актуальными результатами.
* [ ] Негативные прогоны подтверждают: чужой тест не читает секреты/внутреннюю сеть; поддельный артефакт проверки не принимается; push после одобрения и смена SHA делают допуск неактуальным.

h2. Зависимости
Блокируется контрактом module-template/module-applications (LIC-611). Результат нужен доверенной регистрации после merge и проверке последующих релизов. Первичное агентское ревью и пилот LIC-319 переиспользуются как контекст, без дублирования проверки серверной реализации.

h2. Проверка и открытые решения
Сохранить отчёт контрольной заявки и отрицательных сценариев, включая попытку prompt injection и подмены результата. До реализации выбрать границу изоляции, разрешённую сеть, лимиты и формат передачи проверенного результата доверенной части; не обещать конкретный AI-провайдер или готовый скилл.
Вне скоупа: выдача доступа/секретов вендору, регистрация и публикация через API, гарантии безопасности кода конечному пользователю.

h2. Дополнение 21.10.2026 — выбранная схема пилота: GitHub Actions + Docker MikoPBX + Claude
Это уточняет прежний открытый выбор AI-провайдера и основы изоляции. Владелец подтвердил готовые Docker-образы MikoPBX для нужных архитектур и сообщил о предоставленном Anthropic API-кредите $100. Выбран пилот в облаке GitHub на публичном open-source репозитории; агент использует Claude API, стартовый вариант — Claude Agent SDK. Точный образ/digest и доступную модель зафиксировать при реализации. Наличие образов подтверждено владельцем, их запуск в GitHub runner ещё не проверен.

h3. Исполнение и критерии приёмки
* [ ] На новом стандартном GitHub-hosted runner запускается свежий контейнер существующего MikoPBX-образа. Матрица включает заявленные версии MikoPBX и нужные архитектуры, в первую очередь x86_64/arm64 на соответствующих native runners. В отчёте фиксируются версия MikoPBX, архитектура и digest образа.
* [ ] Из source SHA собирается ZIP, сохраняется его checksum; этот пакет устанавливается штатным способом MikoPBX. Проверяются появление/включение модуля, запуск его сервисов и API при наличии, ошибки в логах, функциональные тесты, отключение и удаление, работоспособность MikoPBX после удаления. Для обновления используется известная предыдущая версия; при первой версии отсутствие сценария обновления явно объясняется.
* [ ] Сначала идут детерминированные проверки, затем AI. Общие исходники можно анализировать один раз с приложением результатов обеих архитектур; различающийся код/пакеты не теряются из анализа.
* [ ] Тестовый runner не содержит ключей Anthropic и лицензирования, привилегированных GitHub credentials, доступа к внутренней инфраструктуре. Если образу нужен privileged-контейнер, границей изоляции считается вся одноразовая VM runner; доверенный агент с ключом не запускается на этой же VM. Сеть, mounts и права задаются проверяющим контуром MIKO. После задания окружение уничтожается.
* [ ] Первый агент читает исходники и готовые логи как недоверенные данные и возвращает структурированный отчёт с доказательствами. Он не исполняет код/инструкции модуля рядом с API-ключом, не загружает автоматически его hooks/plugins/MCP/CLAUDE.md как доверенную конфигурацию. Политика и инструменты агента принадлежат MIKO. Дополнительное воспроизведение найденных ошибок при развитии агента выполняется отдельным изолированным исполнителем.
* [ ] Три доверительных этапа разделены: выполнение тестов; AI-отчёт; регистрация после решения человека и merge (LIC-614). Артефакты тестов не дают сами по себе права регистрации; проверяется происхождение и привязка к заявке/SHA. Ошибка теста/агента, таймаут или исчерпанный бюджет означают незавершённую либо неуспешную проверку, а не допуск.

h3. Бюджет и пилот
* [ ] До первого платного запуска проверить в Anthropic Console доступность именно API-кредита, срок действия и ограничения программы для этой задачи. Сумма $100 сообщена владельцем; её баланс, срок и применимость ещё не проверялись. Ключи в Jira, исходники и отчёты не помещать.
* [ ] Первые $10 выделить на калибровку на нескольких известных небольших модулях, включая намеренно сломанный. Зафиксировать пойманные/пропущенные нарушения, длительность, токены, число AI-шагов и фактическую стоимость по Console; оценку SDK не считать окончательным биллингом.
* [ ] После калибровки задать лимиты затрат, шагов и времени на прогон, число повторов и ограничения частоты запусков; не запускать платный AI после очевидного отказа дешёвых проверок. Повтор результата разрешён только при совпадении значимых входов (SHA, checksum, манифест, правила, тестовое окружение и конфигурация агента).
* [ ] Для публичных репозиториев стандартные GitHub-hosted runners не тарифицируются по минутам. Larger runners и хранение сверх квот могут стоить отдельно; задать срок хранения тяжёлых артефактов, сохранив долговечную запись SHA/checksum/решений.
Расчёт обсуждения — $0,45 за три ограниченных AI-прохода и ориентир $0,5–2 за прогон небольшого модуля — не замер и не гарантия цены автономного агента. При фактическом расходе $0,50/$2/$5 кредит $100 покрывает соответственно 200/50/20 прогонов; исправления и повторные проверки расходуют тот же бюджет. Разработка проверяющего набора и время человека отдельно.

h3. Начало работы и источники
Владелец планирует начать разработку 22.10.2026 (Asia/Bangkok); это дата старта по обсуждению, не срок завершения. Начать с получения точных ссылок на образы, одной контрольной заявки и воспроизводимого сценария установки/проверки/удаления, затем подключить AI и замер расхода. Статус, исполнитель, срок и спринт этим дополнением не меняются.
